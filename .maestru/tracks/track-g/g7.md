# G7: Instalador Windows (.exe) completo gerado em Linux

## Objetivo

Gerar, a partir do Linux, um instalador Windows (`.exe`) autónomo que inclui Python, dependências, frontend compilado, MongoDB e serviços, sem pré-requisitos na máquina destino (além de Windows 10/11 ou Server 2019+ 64-bit, CPU com AVX e permissões de administrador).

## Passos do build (em Linux)

1. Compilar o frontend com `npm run build` (resultado independente do SO).
2. Descarregar o Python 3.13 embeddable para Windows e instalar as dependências com `pip --platform win_amd64` (validado: as 26 dependências de `requirements.lock` têm wheels `win_amd64`/cp313).
3. Descarregar o ZIP do MongoDB Community (7.0/8.0) para Windows e o executável do WinSW.
4. Gerar o `.exe` com o Inno Setup, através do Wine ou de uma imagem Docker (por exemplo `amake/innosetup`).

Implementado em `deploy/windows/build-installer.sh` (Wine 11.0 portátil, sem root nem Docker) — ver `deployment-windows`.

## Página de configuração no instalador

- URL da instância (pré-preenchido com `https://cttv8.kanbanize.com`).
- API key em campo mascarado.
- Board inicial (por omissão `96`).
- Porta do site (por omissão `8080`).

Valores gravados apenas no `.env` da instalação (ACL restrita); a API key nunca vai no pacote nem em logs.

## Notas

- Serviços Windows via WinSW: API (Uvicorn), worker, MongoDB; sync agendado.
- MongoDB em `127.0.0.1`, com autenticação e utilizador da aplicação criado com password gerada.
- `backend/app/jobs/worker.py` usa `loop.add_signal_handler` (não suportado em Windows) — resolvido com fallback para `signal.signal`; `EXPORT_DIR` é escrito no `.env` pelo `windows_setup`.
- Desinstalação/atualização preservam a pasta de dados.
- Validado sob Wine (ver `g7-spec`); testes finais numa VM/PC Windows real com AVX ainda por fazer.
- Correção do build: `frontend/src/lib` (`utils.ts`, `format.ts`) estava ignorado pela regra `lib/` do `.gitignore` (agora `/lib/`) e faltava nos clones; o `npm ci` passa a correr também quando `node_modules` está incompleto. Build validado em WSL (Ubuntu 26.04).
- Primeira instalação real (Windows 11): falhou o `windows_setup` (código 1, sem `setup.log`) porque existia uma pasta `.env` em `%ProgramData%\BoardInsight`. Corrigido: o instalador remove pastas vazias no lugar de `.env`/`logs\sync.log`; o `windows_setup` regista sempre o erro no log e devolve 3 em falhas de preparação.
- Após a instalação, o frontend entrava num ciclo de pedidos (milhares por minuto) no fim do primeiro sync: o `SyncButton` voltava a retomar o job terminado a partir do `sync-status` em cache e invalidava todas as queries repetidamente. Corrigido guardando os jobs já terminados (teste de regressão em `SyncButton.test.tsx`).
